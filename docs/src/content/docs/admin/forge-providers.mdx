Hibou supports connecting to multiple Git forges simultaneously. You can even connect multiple instances of the same forge type (e.g., two separate Forgejo servers).

## Supported Forges

| Type | Value | Notes |
|------|-------|-------|
| GitHub | `github` | GitHub.com or GitHub Enterprise |
| Forgejo | `forgejo` | Forgejo instances (v7+) |
| Gitea | `gitea` | Gitea instances (uses same provider as Forgejo) |
| GitLab | `gitlab` | GitLab.com or self-hosted |

## Indexed Configuration Pattern

Each forge is configured via environment variables using a zero-based index:

```
HIBOU_FORGE_{N}_TYPE
HIBOU_FORGE_{N}_ID
HIBOU_FORGE_{N}_URL
HIBOU_FORGE_{N}_CLIENT_ID
HIBOU_FORGE_{N}_CLIENT_SECRET
HIBOU_FORGE_{N}_WEBHOOK_SECRET
HIBOU_FORGE_{N}_EVENT_MODE
HIBOU_FORGE_{N}_POLL_INTERVAL
HIBOU_FORGE_{N}_INVENTORY_INTERVAL
```

Where `{N}` is `0`, `1`, `2`, etc. Hibou reads indexes sequentially and stops at the first gap.

:::note
The `ID` field must be unique across all configured forges. It is used internally to identify the forge and in API responses.
:::

## Multiple Instances

You can configure multiple instances of the same forge type. For example, connecting both a staging and production Forgejo:

```bash
# Staging Forgejo
HIBOU_FORGE_0_TYPE=forgejo
HIBOU_FORGE_0_ID=forgejo-staging
HIBOU_FORGE_0_URL=https://git.staging.example.com
HIBOU_FORGE_0_CLIENT_ID=...
HIBOU_FORGE_0_CLIENT_SECRET=...
HIBOU_FORGE_0_WEBHOOK_SECRET=...

# Production Forgejo
HIBOU_FORGE_1_TYPE=forgejo
HIBOU_FORGE_1_ID=forgejo-prod
HIBOU_FORGE_1_URL=https://git.example.com
HIBOU_FORGE_1_CLIENT_ID=...
HIBOU_FORGE_1_CLIENT_SECRET=...
HIBOU_FORGE_1_WEBHOOK_SECRET=...
```

## Provider Setup

<Tabs>
<TabItem label="Forgejo / Gitea">

### 1. Create an OAuth2 Application

In your Forgejo instance:
1. Go to **Site Administration** → **Applications**
2. Click **Create a new OAuth2 Application**
3. Set:
   - **Application Name**: `Hibou`
   - **Redirect URI**: `http://YOUR_HIBOU_URL/auth/callback`
4. Save and copy the **Client ID** and **Client Secret**

### 2. Configure Webhook Secret

Choose a random string for webhook signature verification:

```bash
openssl rand -hex 32
```

### 3. Environment Variables

```bash
HIBOU_FORGE_0_TYPE=forgejo
HIBOU_FORGE_0_ID=my-forgejo
HIBOU_FORGE_0_URL=https://git.example.com
HIBOU_FORGE_0_CLIENT_ID=<client-id>
HIBOU_FORGE_0_CLIENT_SECRET=<client-secret>
HIBOU_FORGE_0_WEBHOOK_SECRET=<webhook-secret>
```

### API Compatibility

Forgejo and Gitea share the same API. Use type `forgejo` for Forgejo instances and `gitea` for Gitea instances — both use the same underlying provider implementation.

HIBOU_FORGE_0_TYPE=github

### Private GitHub / GHES instances without webhook ingress

Use a GitHub App for machine reads and keep the OAuth credentials above for
interactive login. Choose `poll` explicitly; a missing webhook secret never
automatically changes delivery mode.

```bash
HIBOU_FORGE_0_EVENT_MODE=poll
HIBOU_FORGE_0_APP_ID=<app-id>
HIBOU_FORGE_0_PRIVATE_KEY=<pem-key>
HIBOU_FORGE_0_POLL_INTERVAL=5m
HIBOU_FORGE_0_INVENTORY_INTERVAL=30m
HIBOU_FORGE_0_TIER=report
```

`webhook` is the default. `hybrid` accepts verified webhooks and reconciles
through the API; both need a webhook secret outside development. `poll`
disables the receiver even if a secret remains configured, so deactivate
delivery in the GitHub App settings. No public ingress or relay is required.
Hibou needs outbound API/Git access, and browsers/runners need private
connectivity to Hibou. Existing CI upload commands and token scopes do not
change.

Grant Metadata/Contents read, Pull requests read and Organization Members
read. Actions read enables failed-build reconciliation; without it, pending
builds retain the timeout policy and report the missing capability.
Checks/Statuses write are optional for publishing checks; polling needs no
Contents write. Installations are discovered without an installation event,
but importing an organization requires the signed-in user's current forge
administration. Discovered repositories are not enrolled automatically.

Helm exposes `hibou.forges[].eventMode`, `pollInterval` and
`inventoryInterval`. Server YAML accepts a `forges` list with `event_mode`,
`poll_interval` and `inventory_interval`; indexed environment variables win.
GitHub Enterprise uses its configured API endpoint, including `/api/v3`.

Instance admins can inspect **Settings → Forge delivery** for mode,
freshness, next attempt, denied permissions and rate-limit deferral, and
**Jobs & workers** for run history. The intervals are scheduling targets,
not freshness guarantees. "Sync now" uses the durable scheduler rather than
bypassing backoff.

For hundreds of repositories, unchanged pages use ETags (including installation
inventory), but HTTP headers, TLS and round trips still consume bandwidth.
Inactive discovery uses the slower interval; uploads wake their own repo's
PR/build scopes. Unchanged successful run history is sampled hourly, while
material changes and errors are retained. Reconciliation counts describe
samples, not every successful poll. Explicit shorter intervals are supported
when the API budget and required freshness justify them.

:::caution
Polling cannot inspect a commit pushed and removed between polls. Retain
webhooks or enforce scans in CI/pre-receive when every-push inspection is
required. Neither a successful poll nor a successful workflow proves that
analysis was uploaded or that scan coverage is complete.
:::

## Webhook Verification

Each forge provider validates incoming webhook payloads using HMAC signatures:

| Forge | Header | Algorithm |
|-------|--------|-----------|
| GitHub | `X-Hub-Signature-256` | HMAC-SHA256 |
| Forgejo/Gitea | `X-Gitea-Signature` | HMAC-SHA256 |
| GitLab | `X-Gitlab-Token` | Token comparison |

Requests with invalid or missing signatures are rejected with HTTP 401.
